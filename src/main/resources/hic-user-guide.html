01. How to use this guide

This booklet explains HIC Studio's daily processing, priority sheets, and cancellation decisions. It is bundled with the application and works offline. Open it from Help > User Guide or press F1. You can leave this window open while using the main program. Escape closes the guide.

  • Select a topic in the left-hand Topic Index.
  • Search matches the full instructions, not just titles. Multiple words must all occur in a topic. Matching text is highlighted.
  • Try saved cancellations, unique IDs, not isolating, missed pickups, or an exact button name.
  • Use Clear Search to restore the full index. Previous Topic and Next Topic follow the booklet's original order. Blue links jump to related topics.

Important: cancellation recommendations are decision support, not website actions. Review the donor, quantities, comments, dependencies, and unresolved issues before acting. A recommendation is not evidence that an order was actually cancelled or fulfilled.

New users should start with Daily quick start. For problems, see Input problems, Export problems, or Decision problems.

02. Daily quick start

  1. Open Settings and verify your output directory, template files, and Google Sheet URLs. See Setup and settings.
  2. Copy the day's complete orders from the website's Print view. Paste into Data Input and enter the donor number.
  3. Click Parse & Preview. Inspect request IDs, names, cell types, quantities, request types, comments, and cancellation history. Resolve errors in the Validation tab.
  4. Leave Use Fulfillment Stats enabled when you want website history included in the morning priority workbook. Internet access and a working website session may be needed.
  5. Click Perform All Actions. This generates the summary, apheresis calculations, labels, request lists, priority workbook, and sign-out sheet. Check the Output tab and Generated Files list for completion; review warnings before using the results.
  6. Later, open the red Cancellation Decision button in the blue header. Choose the saved donor/date folder. You do not need to paste the same requests again.
  7. Enter known yields, review dependencies, calculate, and review the suggested actions. Confirm only cancellations or deliveries that actually happened.

Keep the donor folder and its sibling CancellationDecisionState folder together. Use a copy of the output directory for experiments or test runs so you do not overwrite real outcomes.

04. Copying orders from the website

  1. Go to the dispensation page and display the correct day's orders.
  2. Scroll to the bottom and click Print.
  3. Copy everything from the first request ID onward, including complete request rows and their associated comments/history.
  4. Paste into the large Data Input text box, replacing previous input when starting a different batch.

The copied list may be sorted or unsorted. HIC Studio normalizes its order before assigning its own unique IDs. Preserve the fields within each row and keep continuation/history lines attached to their request; do not sort individual text lines by hand.

The gray instructions in an empty input box are placeholder text, not order data. They disappear when you type or paste and return when the box is cleared.

Do not copy only a subset of cell types if you need the planner to understand complete linked orders. A missing PBMC or partner request cannot safely be inferred later. See Preview and validation.

05. Preview, validation, and edits

Parse & Preview converts the pasted text into the editable preview table. The Validation tab reports problems. Verify the request ID, date/time, requester, cell type, maximum, minimum, request type, and requester comment before processing.

  • Request dates use yyyy-MM-dd HH:mm:ss.
  • Quantities must be valid numbers; minimum must not exceed maximum. Use the same units throughout each cell type.
  • The first Row/unique ID column is assigned by the program rather than edited manually.
  • You can correct editable cells in the preview. Changes to website request IDs or cell types are normalized again before generating outputs, and the preview refreshes to match.
  • Re-Parse from Input rebuilds the preview from the pasted text and replaces manual preview corrections. Changing the original pasted text causes it to be parsed again when required.
  • Clearing the preview is not the same as clearing the pasted input; check both before starting a new donor.

Fix the source/preview and regenerate the donor workbook when requests, comments, quantities, or protections change. Editing visible priority-sheet rows in Excel does not update the hidden cancellation-input snapshot.

06. Request IDs and unique IDs

The website's request ID may be shared by several cell-type rows from one requester. HIC Studio also assigns a sequential unique ID to each individual row, starting at 1.

Before assigning unique IDs, it sorts by numeric request ID ascending, then within that request ID by:

  1. Total T
  2. CD4
  3. CD8
  4. Monocytes
  5. NK Cells
  6. PBMC
  7. Unpurified Apheresis Product
  8. Top layer of Ficoll
  9. Bottom pellet of Ficoll

Unlisted types, including B Cells, follow these types alphabetically. Internal names such as CD4+ and Top Layer Ficoll remain unchanged.

The same set of valid requests gets the same unique IDs regardless of paste order. Adding, removing, or changing requests can shift sequential IDs. Output-specific sorts change row positions, not the IDs attached to those requests.

Generate labels and related sheets from the same batch. Do not mix old printed IDs with a newly regenerated request set.

07. Workflow buttons and More Options

The main action strip shows Perform All Actions, More Options, and Clear Output. The red Cancellation Decision button is in the blue header, between HIC Studio and Hide Instructions.

  • Perform All Actions: runs the complete export workflow for the current donor and requests.
  • More Options: expands individual actions: Get HIC Summary, Calculate Apheresis, Make Labels, and Export Sign-Out Sheet. Fewer Options collapses them again.
  • Get HIC Summary: summarizes requests by cell type.
  • Calculate Apheresis: calculates requirements and provides the donor-specific report when usable history is available.
  • Make Labels: generates labels plus the CD4/CD8 request list and low-yield priority workbook.
  • Export Sign-Out Sheet: generates the sign-out workbook using the configured template.
  • Clear Output: clears the displayed output/run summary; it does not delete previously generated files or erase confirmed cancellation outcomes.
  • Hide Instructions: hides the quick-start banner, not this full user guide.

Parse & Preview remains available beside the donor input. More Options hides individual export actions, not the parsing step.

09. Apheresis and donor history

The summary and apheresis tools estimate requirements from the current requests. The Donor Specific Apheresis report additionally uses the configured donor-history sheet when suitable data is present.

Historical rows need valid donor ID, date, cell type, requested_cells, actual_yield, and apheresis_used. Incomplete rows are skipped; selection uses the most recent qualifying history rather than a newer incomplete record. Check the report's source details and warnings before relying on an estimate.

Use consistent units and verify the selected donor. A historical estimate is not an actual measured yield for today's cancellation planning. The cancellation planner does not convert product volumes into cell yields or model shared upstream apheresis consumption.

If a report is missing history, check the URL, access, headers, donor naming, dates, and numeric values. Do not fill missing scientific measurements with arbitrary zeros just to satisfy the parser.

10. Morning priority and fulfillment

Use Fulfillment Stats controls whether the morning label/full-workflow export fetches recent website fulfillment history. The low-yield priority sheets group requests by cell type and show rank, request details, a three-week fulfillment fraction, weekly flags, and missed-pickup stars.

The historical fraction represents fulfilled requests out of fulfilled plus counted cancellations. A lower fulfillment percentage is normally favored. Duplicate/retracted/requester-withdrawn cancellations are excluded from these ranking counts. A cancellation reason of - is not excluded merely because it is a dash.

Weekly tracking uses the collection/current week rather than the original request-submission week. The cancellation planner also considers whether a person has received any cell type, not just the type being ranked.

A sheet rank of #1 is not an absolute promise of fulfillment. Cancellation decisions add protections, weekly-access considerations, donor specificity, linked requirements, and feasibility. See The full cancellation hierarchy.

Missing history is explicitly reported. Verify weekly flags manually if necessary. Lab/Today's Requests protection data must be verified for a usable cancellation snapshot; a failed protection lookup is not treated as proof nobody is protected.

11. Opening Cancellation Decision

  1. Generate the morning donor folder with Perform All Actions or Make Labels.
  2. Click the red Cancellation Decision button in the main header.
  3. Select a recent donor folder or browse to another. Choose the folder containing Low_Yield_Order_Priority.xlsx, not just an arbitrary cancellation export.
  4. Confirm the saved donor, collection date, order count, and generation time.
  5. Work through Yields, Review Dependencies, and Decisions & Outcomes.

The planner loads the morning workbook's saved input snapshot and local outcomes. It does not re-scrape the website or refresh Google Sheets. This keeps later planning quick, but also means source changes after the morning run require regeneration.

Folders created before saved cancellation inputs were supported must be regenerated once. Keep the correct donor/date even when opening a folder on a later day; the selected snapshot determines the collection date.

12. Yields and Not isolating today

Setting in 1 YieldsMeaning
Yield readyEnter a measured total usable yield. Zero means a known zero yield.
Neither option checkedThe yield is unknown. Retained text in a disabled field is ignored.
Not isolating todayKnown zero availability. Yield entry is disabled and linked all-or-none groups cannot be approved for fulfillment.

Enter total usable yield, including amounts already distributed, in the same units as request quantities. Recorded delivered amounts are subtracted exactly once. Do not enter remaining inventory if previous deliveries are also recorded.

With minimum-first enabled, the planner reserves each kept request's minimum and distributes surplus toward maxima. If minimum is zero, maximum is used. Turning minimum-first off requires maximum quantities instead.

Not isolating today can produce cancellation recommendations for cancellable groups, or REVIEW for protected/already committed groups. If that cell type already has recorded positive deliveries, the setting is rejected: use Yield ready with the total actual yield instead.

Unchecking Not isolating returns the type to unknown until Yield ready is selected. Yield values, ready controls, and availability choices currently reset when the planner is reopened. See Closing and resuming.

13. Comments and linked orders

In Review Dependencies, read every requester comment and check the Linked Group, Donor Specific, and Filled This Week fields.

  • CD4/CD8 requests from the same requester are linked automatically and cannot be split in the planner.
  • Conditional comments containing wording such as both, together, all-or-none, or cancel-if can suggest a broader group for that requester's orders.
  • Use the same Linked Group value for requests that must be fulfilled together. Narrow or expand suggested groups to match the actual experiment.
  • Donor-specific, critical-donor, or HLA language can set Donor Specific. Generic urgency such as need cells does not automatically raise priority.
  • Confirm each flagged item individually, or use Select All after reviewing all current items and donor/date/outcomes. It is a shortcut, not automatic verification.

Comment interpretation is heuristic, not complete language understanding. Unrecognized wording still matters and must be reviewed manually. A dash comment does not create an all-or-none link.

An unknown linked yield produces HOLD/provisional reservations, not permission to dispense the known cell type. A known cancelled partner normally cancels pending linked requests. An already fulfilled partner commits the group; impossible commitments require manual review.

14. Keep/cancel priority hierarchy

The planner is a priority-first heuristic, not an exact optimizer. It removes eligible groups contributing to shortages, preserving stronger priorities where feasible, and reconsiders removed groups that can fit.

  1. Hard protections and actual commitments: lab members, matching Today's Requests, and groups containing an already fulfilled member are not automatically recommended for cancellation. Conflicts require REVIEW.
  2. Weekly access: prefer preserving a person's first weekly fulfillment over additional allocations to someone already served or with another genuinely fillable allocation.
  3. Fulfillment history: favor lower historical fulfillment percentage. At tied percentages below 100%, favor more historical cancellations. At 100%, favor fewer total historical requests. Unknown history sorts behind known history at this stage.
  4. Donor-specific tie-breaker: favor the reviewed donor-specific/HLA flag only after weekly access and fulfillment-history factors tie. It no longer overrides a better historical priority.
  5. Missed pickups: fewer stars are favored as a late tie-breaker. Stars never automatically blacklist someone or override stronger protections/priorities.
  6. Request timing: earlier request date/time, then lower request number, break remaining ties.

A linked group inherits its highest-priority member's ranking. Physical feasibility still matters: a 10-cell minimum cannot fit into a 5-cell yield. Minimum-first versus maximum-first changes that feasibility.

The planner cannot guarantee every person is served, the global maximum number of orders is filled, or zero yield is wasted. See Weekly access details and Examples of surprising decisions.

15. What counts as weekly access?

Weekly access means trying to give each requester at least one fulfillment during the collection week's Monday-to-Sunday period. A fulfillment of another cell type can count. Reviewed historical flags and saved actual positive deliveries supplement the morning snapshot.

Another pending order counts as alternative weekly coverage only when all pending cell types in its linked group have known yields and the remaining demand for those types fits available supply after the proposed cancellation.

An unmeasured monocyte request is therefore not a reason to sacrifice someone's high-priority, currently fillable PBMC request. An unresolved or HOLD group is not assumed to provide a real alternative fulfillment.

If a requester will receive known, feasible CD8 cells, their independent NK request may be cancelled to preserve NK for someone who would otherwise receive nothing. This does not make CD8 and NK an all-or-none pair.

Local outcomes contribute only when saved and accessible in the same state-folder location. Planned allocations, checked Will Cancel boxes, and unchecked orders are not proof of actual fulfillment.

16. Understanding decision results

Decisions & Outcomes starts with total yield, already delivered, planned/reserved, and remaining quantities. Negative remaining quantities or unresolved notices require review.

ResultInterpretation
FULFILLThe request fits the current plan. This is not an actual recorded delivery.
CANCEL / SHOULD CANCELA pending cancellation recommendation. It is not submitted to the website or automatically recorded as actual.
HOLDA linked yield is unknown. Reservations are provisional; do not distribute based on HOLD alone.
REVIEWA protection, commitment, conflicting outcome, or shortage prevents a clean automatic decision.
RECORDED FULFILLED / CANCELLEDA previously entered actual outcome, not changed by this recommendation.
NO YIELD ENTERED / LINKED — NO YIELD ENTEREDThe cell type is outside the actionable cancellation list; inspect linked consequences before handling it.

Allocations & Linked Groups: select a row to inspect its entire group and comments below. Needs Your Decision: unresolved issues and linked unknowns. Changes Since Last Calculation: compares decisions/allocations within this open session. Full Details: the complete report, including unmet weekly-access targets.

Changing inputs clears the old displayed recommendation. Calculate again before relying on an earlier result.

For an algorithmic cancellation, Why Cancel starts with Deciding factor. It identifies the actual removal-step rule: unavailable isolation, insufficient yield for the group, protection/commitment constraints, weekly access, or the first differing priority factor. Explanations show demand/supply numbers and comparison values where applicable, and identify linked consequences. Comparison requests can also be cancelled later; the explanation is not a claim that they were ultimately served. Failed restoration checks are stated separately, including unresolved shortages elsewhere in the plan. These explanations are copied into workbook exports and new Decision History iterations.

17. Selecting and confirming cancellations

  1. Calculate, then open Who to Cancel. Its initial recommendations include only pending orders for cell types with known entered yields, including Not isolating today.
  2. Read Why Cancel and Requester Comment. Hover to see long text; scroll horizontally if necessary.
  3. Check Will Cancel for orders you choose to cancel. Recommendations start unchecked. Select All Listed checks the current list.
  4. Use Select Other Orders to add other pending requests, including nonrecommended orders or types without entered yields. They are labelled MANUAL SELECTION. Protected orders are identified; manual selection is not a program recommendation.
  5. After those cancellations actually happen, click the green Confirm & Save Selected Cancellations button. Review the donor/date and named selections, then confirm.

Confirmation records CANCELLED with zero delivered and saves the donor/day outcomes plus current reviewed flags. It does not cancel anything on HIC Cell. Unchecked orders remain unchanged, not automatically fulfilled.

Checkboxes represent temporary intent only. Changing inputs or recalculating clears selections. Closing warns about unconfirmed selected cancellations. Cancelling the confirmation leaves recorded outcomes unchanged.

Saving actual cancellations clears the old recommendation. Review dependencies and recalculate before acting on the next plan.

Select a Who to Cancel row and click View Selected Explanation to read the full deciding factor, comparison, shortage amounts, linked consequences, and requester comment in a scrollable window.

18. Deliveries and saved cancellations

Within Decisions & Outcomes, open Recorded Outcomes & Deliveries. This is the place to review already confirmed cancellations from earlier calculations or sessions for the same donor/day.

  • PENDING: not yet recorded as completed; delivered amount must be zero.
  • FULFILLED: an actual completed delivery; enter a positive actual delivered amount.
  • CANCELLED: an actual completed cancellation; delivered amount must be zero.

Look for Recorded Status = CANCELLED to find previously confirmed cancellations. These are excluded from new Who to Cancel recommendations. The view shows cumulative fulfilled/cancelled/pending counts and whether there are unsaved changes.

Use Save Recorded Outcomes after entering deliveries or correcting previous statuses. Saving asks for confirmation. Merely calculating or checking a cancellation box does not record an outcome.

The saved state reflects current statuses, not an immutable audit trail of later corrections. The workbook's Decision History is a history of calculations, not proof that recommended cancellations actually occurred.

19. PBMCs before later cell types

  1. At the early PBMC stage, mark PBMC Yield ready, enter total usable PBMC yield, and leave later yields unknown unless a type definitely will not be isolated.
  2. Review comments and all-or-none dependencies, then calculate. HOLD is not approval to distribute a PBMC request that still depends on an unknown later yield.
  3. Complete actual website dispensing/cancellations using your normal process. In Who to Cancel, confirm the cancellations that actually happened; Select Other Orders allows exceptions to recommendations.
  4. Record actual PBMC fulfillments and delivered amounts in Recorded Outcomes & Deliveries, then save. Unchecked PBMCs are not automatically assumed fulfilled.
  5. Later, enter isolated-cell yields, review dependencies again, and calculate. Saved PBMC cancellations propagate to linked pending requests; saved PBMC deliveries commit linked partners against automatic cancellation.

The cancellation planner does not check Month View for PBMC outcomes. Enter real outcomes manually. Morning historical-priority scraping is a separate process.

When re-entering PBMC yield after reopening, enter the original total usable yield, not the remainder after the deliveries you have already recorded.

20. Closing, resuming, and backups

Remembered after saving: actual fulfilled/cancelled statuses, delivered quantities, reviewed linked groups, donor-specific flags, and weekly flags for that donor/day.

Not restored: yield values, Yield ready/Not isolating choices, verification checkmarks, temporary Will Cancel selections, and the prior live recommendation display. Re-enter yields/availability, review, and recalculate.

Open the same donor/date folder to resume. Outcomes are stored separately under CancellationDecisionState, beside the donor folders in the output parent directory. The app uses donor/date identity internally; do not manually rename or edit its JSON state files to move outcomes between donors.

Keep the donor folder and its sibling state folder when backing up or moving to another computer. State is not automatically synced between machines. Coordinate one active editor if using shared/copied directories.

Adding/removing requests or changing quantities can require reconciliation. The program rejects saved quantity mismatches rather than silently applying outcomes to changed requests. Back up before corrections and inspect the stated donor/order.

21. Cancellation workbook and history

Each calculation saves one Cancellation_Priority_DONOR_DATE.xlsx in the selected donor folder. Later calculations append numbered iterations to its Decision History instead of creating a new workbook each time.

  • Cancellation Summary: current scoped cancellation recommendations, yields, and warnings.
  • Highlighted priority tabs: original ranking plus decision, planned allocation, reason, and requester comment. Pink SHOULD CANCEL identifies current actionable recommendations. Read the decision text; original priority highlighting remains.
  • Decision History: previous calculations, entered yields, decisions, allocations, comments, groups, protections, and unresolved issues.

The original Low_Yield_Order_Priority.xlsx is preserved. Older randomly named cancellation exports remain archives and are not merged automatically.

Saving runs in the background. Open Highlighted Priority Sheet enables when the current save completes. Export Detailed Notes saves the full text report.

Close the cancellation workbook in Excel before recalculating, then reopen it. Windows can block replacement while it is open; other systems may keep displaying the older opened version. Failed replacement preserves earlier history rather than silently discarding it.

Current cancelled outcomes are reviewed in Recorded Outcomes & Deliveries, not inferred from historical SHOULD CANCEL entries.

22. Why a high-ranked order can cancel

Only 5 NK cells, but a request needs at least 10

Even rank #1 cannot fit an unmet 10-cell minimum into a 5-cell supply. Another requester with a 5-cell minimum may be feasible. Protected requests instead produce an unresolved review requirement.

One requester wants CD8 and NK; another only NK

If the first requester can genuinely receive their independent CD8 request, preserving NK for the second can serve both people once. Without an all-or-none requirement, CD8 and NK do not have to be fulfilled together.

A donor-specific monocyte request competes with historical rank #1

Donor specificity now breaks ties only after weekly access and historical fulfillment factors. A donor-specific comment alone cannot displace someone with a stronger historical priority. If a request requiring both monocytes and Total T does lose its monocytes for another valid reason, the linked T request also cannot be filled, even with enough T cells. Read Deciding factor to distinguish the original shortage decision from its linked consequences.

A requester also has an unknown monocyte yield

The unknown monocyte order does not count as a real alternative weekly allocation. It should not by itself justify cancelling their currently fillable high-priority PBMC request.

Several missed-pickup stars

More stars lower priority only after weekly access, donor specificity, and fulfillment-history factors are equal. They are not an automatic cancellation rule.

Inspect Allocations & Linked Groups, flags, recorded outcomes, and yield settings to explain an individual result. The visible sheet rank alone is not the full cancellation hierarchy.

23. Input and parsing problems

No records parsed, missing rows, or wrong names/cell types

Copy again from the website's Print view, starting at the first request ID. Include full rows and preserve columns and attached continuation lines. Check the original text as well as the preview. Avoid pasting just a formatted summary or a screenshot.

Invalid numeric/date values

Use numeric request amounts and a request timestamp in yyyy-MM-dd HH:mm:ss form. Confirm maximum/minimum columns were not shifted. Correct source or preview and parse/validate again.

Missing requester comments or all-or-none partners

Ensure the copied data includes request type and requester comment fields and all cell types. Comment detection is heuristic: manually review and correct linked groups even when no warning was generated.

Unique IDs differ from older printouts

Check whether the request set changed or the printouts were generated before canonical ID ordering. Regenerate the whole related batch instead of mixing identifiers. Sorting current pasted requests alone should not change IDs for an unchanged valid set.

24. Export, settings, and network problems

Cannot write a file or replace the cancellation workbook

Close the affected Excel/Word file, check the configured output path and folder permissions, and retry. Keep backups. Existing cancellation history is preserved if replacement fails. Reopen the workbook after a successful new save.

Missing template or labels/sign-out failure

Check Settings for the Word label template and Excel sign-out template. Verify the files exist and can be read. Run Setup Wizard if configuration is incomplete; do not store working output inside a replaced application bundle.

Website history or Google Sheet access failed

Inspect Fulfillment, Validation, and the processing output. Verify the URLs, internet connection, access permissions, and any website login/browser prompts. Re-run the morning export after fixing the source. A failed lookup does not imply zero history or no protected requests.

Output looks unchanged

Verify the selected donor/date/output directory and the latest generated file path. Close/reopen Excel. Confirm the action completed successfully instead of relying on a previous open file or old recommendation.

25. Cancellation-planner problems

Folder cannot load, or saved inputs are missing

Select the donor folder containing Low_Yield_Order_Priority.xlsx. Regenerate older folders with Perform All Actions or Make Labels. An arbitrary cancellation workbook alone is not the expected source folder.

Protections not verified

Fix Lab Members/Today's Requests URLs, access, headers, and invalid rows, then regenerate the morning snapshot. The planner does not silently assume unverified protections are absent.

Calculation asks for review

Review the flagged dependencies and donor/date/outcomes in step 2, then select their checks or Select All. Edits reset acknowledgements. Yield ready also requires a valid number; unknown and zero are different.

HOLD, REVIEW, negative remaining yield, or unresolved shortages

Check unknown linked yields, Not isolating settings, protected/committed demand, and actual deliveries. Do not treat provisional reservations as permission to distribute. Correct inputs or resolve the conflict manually; protections are not removed automatically to make totals fit.

Saved cancellation disappeared or an order still looks pending

Verify you confirmed and saved, rather than only checking Will Cancel. Open the same donor/day with its sibling state folder intact, then inspect Recorded Outcomes & Deliveries. Check whether a different computer/output parent directory was used.

PBMC balance is too small after reopening

Enter total usable yield including recorded deliveries. Entering only the remaining inventory causes the recorded amount to be subtracted again.

A new decision disagrees with an old workbook

Compare iteration timestamps, entered yields, availability settings, actual statuses, linked groups, flags, and snapshot age. The live comparison is session-only; use Decision History across sessions. A manually selected cancellation is not an algorithm recommendation.

26. Updates, testing, and safety limits

Use Help > Check for Updates to request an update check. The packaged app also checks shortly after startup. An internet connection is needed for updates, not for reading this guide.

A compatible published normal release with a higher version can prompt for download. Downloading and verification do not install anything without your confirmation. Finish work and save actual outcomes before accepting installation.

  • Windows: the application closes and opens the MSI installer. Follow its prompts, then reopen HIC Studio.
  • Mac: the application closes and opens the DMG. Replace the app in Applications as instructed, then reopen.
  • Draft releases and prereleases are not offered by the normal updater. Download a test installer manually when testing an unpublished build.
  • The standard Windows MSI upgrades the existing app; it is not a separate test installation. Use a copied output/state directory for test data and keep backups.

Limits: outcomes are local, not automatically synchronized; a request row has one complete recorded status, not partial fulfillment; comment interpretation needs human review; allocation is not a mathematical guarantee of maximum orders or zero waste; no cancellation-planner action changes orders on the website.

If a result still cannot be explained, preserve the donor workbook and note the application version, donor/date, entered yields/availability, recorded outcomes, and exact warning. Use test copies when investigating, not live outcome records.
